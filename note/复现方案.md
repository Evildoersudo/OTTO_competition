

我建议你的复现版本严格按下面这条链走：

```text
OTTO Train
    │
    ├── Validation 构造
    │
    ├── Session History Recall
    │
    ├── 10组 Co-visitation Matrix
    │        ↓
    │   多种 Chain Recall
    │
    ├── 8组 NN Embedding Recall
    │
    └────────────┬─────────────
                 ↓
          Candidate Union
                 ↓
           Feature Engineering
                 ↓
       ┌─────────┼─────────┐
       ↓         ↓         ↓
    Click LGBM Cart LGBM Order LGBM
       ↓         ↓         ↓
             Ensemble
                 ↓
       Click/Cart/Order Top20
                 ↓
          OTTO Joint Recall
```

这和作者公开的 `run_train_all.sh` 完全一致：**Co-visitation → aid/session statistics → NN → candidates + reranker data → reranker**。([GitHub][2])

---


# 第二阶段：复现 Session History Recall

这是最简单的一路，但不要删。

对于：

```text
A click
B click
C click
B cart
D click
```

Candidate 先包含：

```text
A B C D
```

同时第一名会产生：

```text
isin_0_count
isin_0_clicks
isin_0_carts
isin_0_orders

isin_0_rank

isin_0_ts_diff_pre
isin_0_ts_diff_post
```

也就是说：

> **Session 内历史商品既是候选，也提供 Session×Item 特征。**

作者代码确实对每个 session 内 aid 聚合了出现次数、click/cart/order 数量、最近位置和前后时间差等信息。([GitHub][4])

这一路你可以称作：

```text
Recall #0
Session History Recall
```

# 第三阶段：完整复现 Co-visitation Recall

这一阶段是 OTTO 第一名里最值得你好好学习的。

作者不是：

```text
一张 ItemCF
```

而是训练了：

```text
v11
v12
v13
v14
v15
v16
v17
v18
v19
v20
```

**10 个 Co-visitation 版本。**([GitHub][5])

不同版本改变：

```text
行为权重

时间窗口

商品对之间允许的时间距离

是否强调 click/cart/order

每个商品保留多少邻居

统计方式
```

你先不要急着理解为什么是 v11、v14、v20。

把它们理解成：

```text
Co-vis #1：偏普通共现

Co-vis #2：偏 Click

Co-vis #3：偏 Cart

Co-vis #4：偏 Order

Co-vis #5：偏近期行为

...
```

就可以。

# 第四阶段：复现 Chain Recall

这一点比普通 ItemCF 更重要。

第一名不是简单：

```text
A
↓
Co-vis
↓
B
```

还会：

```text
A
↓
B
↓
C
```

甚至：

```text
A
↓
B
↓
C
↓
D
```

代码里作者自己写得非常清楚：

```text
apply covisitation at multiple time
```

并且每一轮保留部分候选继续向下一层搜索。([GitHub][4])

你可以理解为：

```text
Session Items
     │
     ▼
  第一跳
Top Neighbor
     │
     ▼
  第二跳
Top Neighbor
     │
     ▼
  第三跳
...
```

这就是一种类似 Beam Search 的 Candidate Expansion。

---

# 第五阶段：完整复现不同 Chain 策略

第一名这里实际上做得非常“暴力”。

比如：

```text
11_p_chain_full_20_5
11_p_chain_full_100_5
```

以及：

```text
11_p_chain_all_20_2
12_p_chain_all_20_2
...
17_p_chain_all_20_2
```

还有：

```text
11_14_chain_1_2dic
11_14_chain_2_2dic
11_14_chain_3_2dic
```

等等几十路 Candidate Feature。([GitHub][1])

不用被这些名字吓到。

它们大致是在改变三个东西：

### ① 从 Session 哪些 Item 出发

比如：

```text
最后 1 个
最后 3 个
最后 5 个
最后 7 个
最后 9 个
```

代码确实使用：

```text
ran = [1,3,5,7,9]
```

作为不同起始范围。([GitHub][4])

### ② 每一步保留多少中间候选

比如：

```text
20
100
```

### ③ 走几跳

比如：

```text
2 hop
5 hop
```

# 第六阶段：双 Co-visitation Chain

第一名还有一个很漂亮的设计：

```text
Co-vis Matrix A
      ↓
第一跳
      ↓
第二跳
      ↓
切换
      ↓
Co-vis Matrix B
      ↓
下一跳
```

例如：

```text
Click-oriented Co-vis
        ↓
寻找用户可能进一步浏览什么
        ↓
Order-oriented Co-vis
        ↓
寻找可能购买什么
```

代码里的函数就叫：

```text
get_from_count_dic_chain_p_full_switch
```

并明确说明会在指定 iteration 切换另一张 covisitation dictionary。([GitHub][4])

这个以后非常值得你做消融：

```text
single covis
vs
chain covis
vs
switch covis
```

---

# 第七阶段：复现 NN Embedding Recall

Co-visitation 全跑完之后，再进入 NN。

第一名不是训练一个 NN，而是：

```text
v15
v18
v21
v23
v27
v29
v31
v42
```

**8 个 Embedding Model。**([GitHub][6])

每个模型针对：

```text
clicks
carts
orders
```

分别生成候选。

可以先把 NN 部分抽象成：

```text
              Session
                 │
                 ▼
          Session Encoder
                 │
                 ▼
         Session Embedding
                 │
          cosine similarity
                 │
                 ▼
          Item Embeddings
                 │
                 ▼
              Top200
```

第一名候选代码默认读取 NN 的 Top200 结果，并同时保留对应 similarity score。([GitHub][4])

所以：

```text
NN Candidate
+
NN Similarity
```

同时产生。

---

# 第八阶段：这里才把所有候选合并

现在对于一个 session：

```text
Session History
        │
        ├── A B C D
        │
Co-vis v11
        ├── E F G ...
Co-vis v12
        ├── F H J ...
...
Chain Recall
        ├── K L M ...
NN v15
        ├── N F O ...
NN v18
        ├── E P Q ...
...
```

全部做：

[
C_s=C_{history}\cup C_{covisit}\cup C_{NN}
]

得到最终 Candidate Pool。

这里**不要加热门召回**。

我们就忠实保持：

```text
History
+
Co-visitation
+
NN
```

三大类。

---

# 第九阶段：召回完成以后，先测 Candidate Recall

这一点我强烈建议你自己补上。

不要一做完候选就急着训练 LightGBM。

先算：

```text
Candidate Recall@click

Candidate Recall@cart

Candidate Recall@order
```

并逐步记录：

```text
History only

History
+ Co-vis

History
+ Co-vis Chain

History
+ Co-vis Chain
+ NN
```

比如你以后应该形成这样的实验表：

| Candidate | Click Recall | Cart Recall | Order Recall |
| --------- | -----------: | ----------: | -----------: |
| History   |          ... |         ... |          ... |
| + Co-vis  |          ... |         ... |          ... |
| + Chain   |          ... |         ... |          ... |
| + NN      |          ... |         ... |          ... |

这样你才能真正理解：

> **哪一路召回到底贡献了什么。**

否则你只是把第一名脚本执行了一遍。

# 第十阶段：统计特征

这时候开始进入 Feature Engineering。

第一名官方训练流程会依次运行：

```text
aid_feats.py 1
aid_feats.py 2
aid_feats.py 3

h_aid_feats.py
h_aid_feats_v2.py

session_feats.py
session2h.py
```

也就是说会构造：

```text
Item Features

Item × Time Features

Session Features

Session × Time Features
```

等各种统计量。([GitHub][7])

---

# 第十一阶段：Item 特征

主要描述：

> 这个商品本身是什么状态？

例如：

```text
aid 被交互次数

出现过多少 Session

click 数

cart 数

order 数

click rate

cart rate

order rate
```

以及不同时间窗口的统计。

这些东西你应该全部保留。

这虽然里面包含：

```text
popularity
```

概念，但注意：

> 这是 **Popularity Feature**，不是 **Popularity Recall**。

这是两回事。

---

# 第十二阶段：时间热度 Feature 也保留

例如第一名 Click Ranker 里直接包含：

```text
ah_popular_6_True_clicks
ah_popular_24_True_clicks
ah_popular_48_True_clicks

ah_popular_24_True_carts
ah_popular_24_True_orders
...
```

这些显然描述的是：

```text
某个 aid
在最近某个时间窗口
有多热门
```

它们是 Ranker Feature。([GitHub][8])

所以我建议：

```text
❌ Popularity Recall
```

不要。

但是：

```text
✅ Item Popularity Features
✅ Time-window Popularity Features
```

必须保留。

否则你就不是在复现第一名了。

---

# 第十三阶段：Session 特征

例如：

```text
session length

click 数量
cart 数量
order 数量

重复 item 比率

时间密度

最后一次行为时间间隔
```

第一名 Ranker 特征中可以直接看到：

```text
u_aid_dup_rate
u_last_ts_diff
u_time_density
u_carts_rate
u_clicks
u_clicks_rate
u_length
```

等字段。([GitHub][8])

这些描述的是：

> 这个用户目前处于什么购物状态。

---

# 第十四阶段：召回分数全部成为 Feature

这是第一名方案最应该学的地方之一。

例如：

```text
candidate X
```

可能拥有：

```text
co-vis v11 score
co-vis v12 score
co-vis v15 score

chain hop1 rank
chain hop2 rank

NN v15 click cosine
NN v18 click cosine
NN v42 order cosine

isin_session
...
```

全部作为：

```text
(session,item)
```

的特征。

所以你可以把整个第二阶段理解为：

```text
Candidate Generator
不仅产生 Candidate

还产生
Candidate Features
```

这就是召回和 Ranking 真正连接起来的地方。([GitHub][8])

---

# 第十五阶段：训练三个 LightGBM Ranker

然后分别训练：

```text
Click LGBMRanker

Cart LGBMRanker

Order LGBMRanker
```

第一名使用 `LGBMRanker`，并通过：

```python
group=get_group(sessions)
```

告诉 LightGBM：

```text
哪些 Candidate 属于同一个 Session
```

因此它做的是 Learning-to-Rank，不是简单 point-wise classification。([GitHub][8])

训练标签就是：

```text
label_clicks
label_carts
label_orders
```

三个任务分别训练。([GitHub][8])

---

# 第十六阶段：负采样

因为：

```text
Candidate 可能几百/上千
```

但：

```text
Positive
只有极少数
```

所以负样本数量巨大。

第一名 Ranker 代码会：

```text
保留 positive
+
采样一部分 negative
```

然后再训练 LGBMRanker。公开代码中 full training 的确设置了负样本采样比例。([GitHub][8])

这部分你也不要删。

它其实就是工业推荐非常经典的：

> Candidate-level Negative Sampling。

# 第十七阶段：不是三个 Ranker，而是九套 Ranker 配置

完整第一名会执行：

```text
v1
v2
v3
v4
v5
v6
v7
v8
v9
```

9 个 Ranker version。([GitHub][9])

然后：

```text
Clicks
Carts
Orders
```

分别获得多套模型结果。

最终 Ensemble。

所以真正结构是：

```text
                     Candidates
                         │
                         ▼
                      Features
                         │
       ┌─────────────────┼─────────────────┐
       ▼                 ▼                 ▼
     Ranker v1         Ranker v2  ...    Ranker v9
       │                 │                 │
       └─────────────────┼─────────────────┘
                         ▼
                     Ensemble
                         ▼
                       Top20
```

# 我建议你实际怎么复现

不要一次把几十个脚本全研究完。

你的开发顺序我建议固定成下面这样：

1. **数据 + Validation + Metric**
2. **Session History Candidate**
3. **Co-visitation v11–v20**
4. **Chain Co-visitation**
5. **Candidate Recall 评测**
6. **8 个 NN Recall**
7. **再次评测 Candidate Recall**
8. **Item / Time / Session Statistics**
9. **构造 `(session,item)` Ranking Dataset**
10. **三个 LGBMRanker**
11. **9 版本 Ranker**
12. **Ensemble**
13. **生成 Kaggle submission**

这套顺序实际上就是第一名完整工程的依赖关系。([GitHub][2])

## 第一轮先做到哪里？

我建议你的**第一个明确里程碑**不是把整个第一名跑完，而是做到：

```text
OTTO Data
   ↓
Validation
   ↓
v11~v20 Co-vis Matrix
   ↓
Session History + Co-vis Chain
   ↓
Candidate Pool
   ↓
Candidate Recall
```

也就是**暂时停在召回阶段**。

等我们确认：

```text
哪些 Co-vis 有效？
为什么有效？
Chain Recall 到底怎么工作？
Candidate Recall 是多少？
```

再进入 NN Recall。

这是最适合学习的切法，因为 **Co-visitation + Chain Candidate Generation 是第一名方案最基础、也是后面所有 Ranker 的地基**。

下一步我建议我们直接开始拆 **`covisitation.py`**：我可以按照第一名代码，把 **v11 到 v20 每一个 Co-visitation Matrix 到底怎么算、输入输出是什么、为什么要设计这么多版本**逐个讲清楚，然后我们再开始写你的复现版本。
