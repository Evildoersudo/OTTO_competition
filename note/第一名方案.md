
> **OTTO 第一名并不是靠一个特别复杂的端到端深度模型取胜，而是一个非常典型的“多路召回 → 大量特征 → Learning-to-Rank → 模型融合”系统。**

作者自己的训练脚本甚至直接按这个顺序执行：

```text
Covisitation
    ↓
Item / Session Statistics
    ↓
Neural Network Retrieval
    ↓
Candidate Generation + Feature Construction
    ↓
LightGBM Ranker
```

这是作者公开代码中 `run_train_all.sh` 的实际流程。([GitHub][1])

我先不给你陷入各种 `v11/v15/v42` 版本号，而是先把**第一名到底在干什么**讲清楚。

---

# 一、先看第一名整体 Pipeline

你可以把它理解成：

```text
                 用户当前 Session
                        │
                        ▼
        A click → B click → C cart → D click
                        │
       ┌────────────────┼───────────────────┐
       │                │                   │
       ▼                ▼                   ▼
 Session历史      多种 Co-visitation       NN召回
 当前出现过的商品     共现召回          Embedding召回
       │                │                   │
       └────────────────┼───────────────────┘
                        │
                        ▼
                 Candidate Pool
                  大量候选商品
                        │
                        ▼
              为每个 (session,item)
                  构造大量特征
                        │
        ┌───────────────┼────────────────┐
        │               │                │
   召回特征       Session-Item特征    统计/时间特征
        │               │                │
        └───────────────┼────────────────┘
                        │
                        ▼
              3个 LightGBM Ranker
              /         |         \
             /          |          \
        Click         Cart        Order
        Ranker        Ranker      Ranker
             \          |          /
                        ▼
                多模型 Ensemble
                        │
                        ▼
              Click / Cart / Order
                   各 Top20
```

所以你可以先记：

> **第一名 = Recall + Feature Engineering + LGBM Ranking + Ensemble。**

深度学习模型只是其中的**一路召回器**，并不是整个系统的最终 Ranker。([GitHub][2])

---

# 二、第一阶段：Candidate Generation

这是整个方案非常重要的一部分。

原因你现在已经能理解：

OTTO 有一百多万个商品，但是最终：

```text
每个 session
↓
只需要 Top20
```

所以第一阶段不是精确判断谁应该排第 1，而是：

> **尽量把真正的 Click / Cart / Order 商品放进候选集合。**

如果 Ground Truth 是：

```text
真实 order = X
```

但你的召回：

```text
Candidates = A B C D E ...
```

里面没有 X，那么 LightGBM 再厉害也救不回来。

因此这里最关心的是：

$$
Candidate\ Recall
$$

第一名主要用了三大类候选。

---

# 三、召回 1：Session 本身出现过的商品

这是一个非常朴素但很重要的召回。

假如用户：

```text
A click
B click
C click
B cart
D click
```

那么：

```text
A
B
C
D
```

全部直接加入 Candidate。

因为在电商场景中：

> 用户已经点击过、特别是已经加购过的商品，本身就很可能之后购买。

而且作者并不是简单地：

```text
candidate = B
```

还顺便构造了 B 在当前 session 中的特征，例如：

```text
B出现次数

B点击次数

B加购次数

B购买次数

B距离Session尾部的位置

B前一次/后一次行为的时间间隔
```

代码里明确统计了 `rank`、`count`、`clicks`、`carts`、`orders`、前后时间差等信息。([GitHub][2])

这个东西非常重要。

比如：

```text
Session 1：

A click
B click
C click
B cart
D click
```

对于候选 B：

```text
出现次数 = 2
cart次数 = 1
距离当前很近
```

对于候选 A：

```text
出现次数 = 1
cart次数 = 0
距离当前比较远
```

那么很明显：

```text
P(B被购买) > P(A被购买)
```

这些信息就交给 LightGBM 学。

---

# 四、召回 2：Co-visitation，是第一名非常核心的一部分

这部分你可以理解成一个加强版 ItemCF。

假设大量 session 中：

```text
A → B
A → B
A → C
A → B
A → D
```

那么得到：

```text
A → B  score很高
A → C
A → D
```

如果当前 session 出现了 A：

```text
A
↓
Co-visitation
↓
B C D ...
```

作为候选。

但第一名**不是只建立一张 Co-visitation Matrix**。

它构造了很多不同版本。([GitHub][3])

这才是第一名方案比较有意思的地方。

---

# 五、为什么要构造很多张 Co-visitation Matrix？

因为：

```text
click
cart
order
```

代表的购买意愿不同。

作者使用了不同的行为权重。

例如基础版本：

```text
click  = 1
cart   = 3
order  = 6
```

另外还有：

```text
click = 1
cart  = 9
order = 1
```

或者：

```text
click = 1
cart  = 0
order = 0
```

甚至：

```text
click = 1
cart  = 15
order = 20
```

并且不同版本还改变：

* 只使用最近 14 天数据；
* 向前看多少个 item；
* 每个 item 保留 Top100 或 Top300 共现商品。([GitHub][3])

你可以理解成作者故意构造：

```text
偏 Click 的 Co-visitation

偏 Cart 的 Co-visitation

偏 Order 的 Co-visitation

近期趋势 Co-visitation

短距离 Co-visitation

长距离 Co-visitation
```

这就是非常典型的：

> **多路召回。**

---

# 六、这里还有一个很值得学的东西：多跳 Co-visitation

普通 ItemCF：

```text
A
↓
B
```

找到和 A 最相关的 B。

第一名还会继续：

```text
A
↓
B
↓
C
```

甚至：

```text
A
↓
B
↓
C
↓
D
```

作者代码里面直接把这个函数注释为：

> 多次应用 covisitation。

并且中间只保留一批较好的候选继续向下扩展，有点像 Beam Search。甚至可以在中途切换另一张 Co-visitation Matrix。([GitHub][2])

举个例子。

当前：

```text
用户看了：

iPhone
```

第一跳：

```text
iPhone
↓
手机壳
充电器
AirPods
```

再从：

```text
手机壳
```

找到：

```text
钢化膜
```

从：

```text
AirPods
```

找到：

```text
AirPods保护壳
```

于是最终候选扩大：

```text
手机壳
充电器
AirPods
钢化膜
AirPods保护壳
...
```

所以它实际上利用了 item graph 中的：

> **多跳邻居。**

---

# 七、召回 3：Neural Network Embedding Recall

这个部分非常容易被误解。

第一名确实用了神经网络，但是**NN 并不是最终负责 Top20 排序的模型**。

它主要负责：

> **学习 Session Embedding 和 Item Embedding，然后做向量召回。**

基本思想类似：

```text
Session
↓
NN
↓
Session Embedding
       ↓
   cosine similarity
       ↓
所有 Item Embedding
       ↓
TopK
```

作者在推理代码里就是：

1. 预先得到全部商品 embedding；
2. 计算当前 session embedding；
3. L2 normalize；
4. 做矩阵乘法得到 cosine similarity；
5. 取 Top-K 商品和分数。([GitHub][4])

也就是说：

[
score(s,i)
==========

\cos(e_s,e_i)
]

---

# 八、更有意思的是：它对 Click / Cart / Order 建不同的 Session 表示

这个设计很值得注意。

因为同一个 session：

```text
A click
B click
C cart
D click
```

如果我要预测：

```text
next click
```

和我要预测：

```text
order
```

兴趣表示不应该完全一样。

所以作者引入了：

```text
label_type embedding
```

把：

```text
Click type embedding
Cart type embedding
Order type embedding
```

加入 Session Embedding。

大致可以理解成：

```text
             Session Encoder
                    │
                    ▼
             Base Session Emb
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
   +Click Emb    +Cart Emb    +Order Emb
       │            │            │
       ▼            ▼            ▼
  Click Session  Cart Session Order Session
  Embedding      Embedding    Embedding
```

代码里正是把 `label_type embedding` 加到 session embedding 上，再和 target item embedding 计算相似度。([GitHub][4])

所以：

```text
同一个 Session
```

会生成：

```text
面向 Click 的召回

面向 Cart 的召回

面向 Order 的召回
```

这很符合 OTTO 的 Multi-Objective 特征。

---

# 九、而且 NN 不止训练了一个

第一名最终候选里加载了多个 NN embedding 模型版本，例如：

```text
v15
v18
v21
v23
v27
v29
v31
v42
```

并且分别得到：

```text
click candidates
cart candidates
order candidates
```

通常保留约 Top200 的 NN 候选及相似度分数。([GitHub][2])

所以最终并不是：

```text
一个 NN
```

而是：

```text
多个 Co-visitation Recall
+
多个 NN Recall
+
Session History Recall
```

共同组成候选池。

# 十、接下来才进入这个比赛真正特别“特征工程”的部分

假设：

```text
Session 123
```

通过所有召回渠道找到了：

```text
Candidate:
A
B
C
D
E
F
...
```

那么现在数据就转换成：

```text
(session, candidate_item)
```

一行一个训练样本：

| session | candidate |
| ------- | --------- |
| 123     | A         |
| 123     | B         |
| 123     | C         |
| 123     | D         |

然后对每一行构造大量 Feature。

这就是第一名的第二阶段。

---

# 十一、第一类 Feature：召回分数

这个非常值得你学习。

假设候选 B：

```text
Co-visitation A：
rank = 2
score = 87

Co-visitation B：
rank = 5
score = 42

NN click：
rank = 3
cosine = 0.81

NN order：
rank = 10
cosine = 0.63
```

这些**不是直接手动加起来**。

而是全部变成：

```text
Feature
```

交给 LightGBM。

这其实是非常关键的思想：

> **召回模型本身输出的 score/rank，也是一种特征。**

作者最终 Ranker 的特征列表里可以直接看到大量：

```text
count_dic_vxx...
emb_clicks_vxx
emb_carts_vxx
emb_orders_vxx
```

也就是各种 Co-visitation 和 Embedding 召回结果。([GitHub][5])

---

# 十二、第二类 Feature：Session × Item 特征

比如候选 B：

```text
B 是否出现在当前 session？

B 在 session 中出现多少次？

B click 多少次？

B cart 多少次？

B order 多少次？

最近一次 B 距离当前有多远？

B 最后出现的位置是多少？
```

这类特征非常符合用户当前意图。([GitHub][2])

例如：

```text
候选 X

NN score一般
Co-vis score一般

但是：

X刚刚被用户cart过
```

那么：

```text
Order Ranker
```

完全可能把 X 排到最前面。

这就是为什么只看召回分数不够。

---

# 十三、第三类 Feature：Item 全局统计

比如：

```text
item被交互多少次
item出现在多少个session
item被click多少次
item被cart多少次
item被order多少次
```

而且还不是只算全局。

作者还会统计：

```text
最近14天

最近28天
```

的商品热度。([GitHub][6])

比如：

```text
商品A

过去总体很热门
但最近完全没人买
```

和：

```text
商品B

总体一般
但最近突然爆火
```

这两个商品的未来点击/购买概率显然不同。

所以：

> **时间窗口统计特征**

也是一个重要部分。

---

# 十四、第四类 Feature：Session 特征

作者还描述当前 session 本身：

```text
session长度

unique item比例

当前时间

最后两个行为间隔

整个session持续时间

行为密度

click数量

cart数量

order数量

click/cart/order占比
```

这些都直接出现在代码中。([GitHub][7])

这其实是在告诉模型：

> 这个用户当前到底处于什么购物状态？

比如：

### Session A

```text
20 clicks
0 carts
0 orders
```

可能属于：

> 随便逛逛。

而：

### Session B

```text
5 clicks
3 carts
```

明显更像：

> 即将购买。

那么 Order Ranker 对同一个 candidate 的判断可以不同。

---

# 十五、还有时间 × Item 的交叉统计

作者的最终 Ranker 特征里还能看到大量：

```text
ah_popular_xxx_clicks

ah_popular_xxx_carts

ah_popular_xxx_orders
```

也就是把**时间段和商品热度结合起来**。([GitHub][5])

你可以简单理解：

```text
item A

早晨热门
晚上不热门
```

因此：

```text
当前 Session 发生时间
×
Item的时间热度
```

也可以成为预测信号。

---

# 十六、最终 Ranker：不是普通 LightGBM，而是 LGBMRanker

现在：

```text
(session,item)
```

已经有大量特征：

```text
Recall Features
+
Session-Item Features
+
Item Statistics
+
Session Statistics
+
Time Features
```

然后第一名使用：

> **LightGBM LGBMRanker**

做 Learning-to-Rank。([GitHub][5])

这里和普通二分类稍微不同。

不是简单问：

```text
item会不会被购买？
```

而是：

> 对同一个 session 里的这一堆 candidate，谁应该排在前面？

训练数据类似：

```text
Session 123

candidate   label
A             0
B             1
C             0
D             1
E             0
```

LightGBM 知道：

```text
A B C D E
```

属于同一个：

```text
Session 123
```

作者代码里明确通过 `group=get_group(sessions)` 按 session 组织 ranking group。([GitHub][5])

这就是标准的：

> **Learning to Rank。**

---

# 十七、Click / Cart / Order 是三个独立 Ranker

这一点也非常重要。

并不是：

```text
一个 LightGBM
↓
同时预测三种行为
```

而是：

```text
            Candidates
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
 Click Ranker Cart Ranker Order Ranker
       │         │         │
       ▼         ▼         ▼
Click score  Cart score Order score
```

代码明确把：

```text
clicks → label 0
carts  → label 1
orders → label 2
```

分别训练 `LGBMRanker`。([GitHub][5])

而且它们使用的 Feature Set 也可以不同。

比如 Order Ranker 很自然会特别重视：

```text
isin_cart
order-oriented covisitation
order embedding similarity
item order popularity
```

而 Click Ranker 可以更多关注：

```text
click covisitation
click NN score
recent item
click popularity
```

---

# 十八、最后还有 Ensemble

第一名最后并不是只用一个 LightGBM。

作者公开的 inference 脚本加载：

```text
v1
v2
v3
...
v9
```

共多个 Ranker 版本，对：

```text
Clicks

Carts

Orders
```

分别进行 ensemble，最后再产生提交结果。([GitHub][8])

所以完整结构实际上是：

```text
                         Candidate
                             │
                             ▼
                         Features
                             │
         ┌───────────────────┼───────────────────┐
         ▼                   ▼                   ▼
     LGBM v1             LGBM v2 ...         LGBM v9
         │                   │                   │
         └───────────────────┼───────────────────┘
                             ▼
                          Ensemble
                             ▼
                           Top20
```

# 十九、现在重新看第一名，你会发现它的核心并不神秘

可以压缩成四件事情：

### 1. 召回一定要广

```text
Session History
+
大量不同 Co-visitation
+
多跳 Co-visitation
+
多个 NN Embedding Models
```

目的是：

> Ground Truth 尽可能进入 Candidates。

### 2. 召回结果不仅是候选，也是 Feature

```text
Co-vis score
Co-vis rank

NN cosine
NN rank
```

全都进入 Ranker。

### 3. 大量人工统计 Feature 补充信息

```text
Session × Item

Item popularity

Session state

Time statistics
```

### 4. 最终交给 LGBMRanker 学怎么组合

而不是人手写：

```text
0.3 × co-vis
+ 0.4 × NN
+ 0.3 × popularity
```

让：

```text
LightGBM
```

自己学习非线性组合。

# 二十一、这也回答了你上一轮的疑问：OTTO 是不是重点在特征工程？

**是，但我会稍微修正一下：**

OTTO 第一名最值得你学习的是：

> **召回工程 + 特征工程 + Learning-to-Rank。**

而不是单独“特征工程”。

我甚至会把重要程度理解成：

```text
候选召回
   ↓
决定模型的上限

特征工程
   ↓
决定 Ranker 能看见什么信息

LGBM Ranker
   ↓
学会组合这些信息

Ensemble
   ↓
再挤最后一点性能
```

因为对于 Recall@20：

```text
Ground Truth
没有进入 Candidate
↓
后面的 Feature / Ranker 全部无意义
```

所以**召回质量一定是第一道生命线**。

# 二十二、还有一个很重要的认识：深度学习不是来“替换传统推荐”的

第一名这个方案特别适合你目前学习推荐系统。

它告诉你：

```text
Co-visitation
并没有被 NN 淘汰

NN
也没有把 GBDT 淘汰
```

而是：

```text
Co-visitation
      \
       \
Session History ───→ Candidate Generation
       /
NN Recall
       \
        ↓
所有结果变成 Feature
        ↓
LightGBM Ranker
```

**不同模型解决不同阶段的问题。**

这其实比单独学 SASRec、GRU4Rec 更接近工业推荐系统。

# 二十三、如果你准备自己做 OTTO，我不建议直接复现完整第一名

作者完整方案非常重，公开代码说明训练流程本身就是 Covisitation、统计特征、多个 NN、二阶段数据、多个 Ranker 的组合。([GitHub][1])

你现在比较合理的第一版应该缩成：

```text
                  Session
                     │
         ┌───────────┼──────────┐
         ▼           ▼          ▼
 Session History  Co-visitation Popularity
         │           │          │
         └───────────┼──────────┘
                     ▼
                 Candidates
                 Top100~300
                     │
                     ▼
                  Features
                     │
      ┌──────────────┼─────────────┐
 Session-item     Item stats    Recall score
                     │
                     ▼
              3 × LGBMRanker
                     │
                     ▼
                  Top20
```

第一版**先别上 NN recall**。

等这一版跑通之后，再：

```text
V2
+
NN Embedding Recall
```

然后：

```text
V3
+
更多 Co-visitation
+
多跳召回
```

再：

```text
V4
+
更多时间统计
+
更多 Ranker
+
Ensemble
```

这样你不是在机械复现一个比赛答案，而是在真正学习一个推荐系统是怎么从：

**召回 → 特征 → 排序 → 融合**

逐步构建起来的。

而且我认为接下来最值得我们继续拆的是**第一名的 Co-visitation Candidate Generation**：它看起来代码里版本一大堆，但核心其实就是“**共现矩阵到底怎么构造 → 为什么要按 click/cart/order 加权 → 一个 Session 到底怎么从它生成候选 → chain recall 又是什么**”。把这一块彻底搞懂之后，你基本就真正进入“召回工程”这一层了。
